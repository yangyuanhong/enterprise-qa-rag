# EnterpriseQA 企业知识库问答系统 · 面试案例

本文整理自项目开发过程中实际排查过的问题。每个案例按“现象 → 排查 → 根因 → 方案 → 效果”组织，最后附面试官可能的追问。

## 项目一句话介绍

基于 Flask + Vue 3 的企业内部知识库问答系统。支持 txt / md / pdf / docx / csv 上传，统一转成 Markdown 后按章节、表格、图片分别切分，写入 Chroma；问答时用向量检索加关键词检索召回，bge-reranker 重排，再由本地 qwen3:8b 通过 LangChain Agent 生成带引用来源的回答。文档解析和向量化在后台任务中执行，前端实时显示进度。

技术栈：Flask、SQLAlchemy、MySQL、Chroma、LangChain 1.x、Ollama（qwen3:8b、qwen3-embedding:4b、qwen3-vl:8b-instruct）、pymupdf4llm、fastembed（bge-reranker-v2-m3）、Vue 3 + Element Plus。

## 使用说明

- 讲案例时重点讲排查过程：怎么发现的、看了哪些中间结果、怎么确认根因。只讲结论的话，面试官很难判断是不是你自己做的。

## 一、文档解析与切分

### 案例 1：CSV 按长度切分丢失表头

**现象**：API 错误码表（18 行）用 `RecursiveCharacterTextSplitter` 切成 3 块。第 2、3 块里只有 `| 20003 | 423 | 用户模块 | 账号已锁定 |` 这样的数据行，没有表头；块与块之间的 overlap 还让有些行重复出现了两次。

**根因**：通用的文本切分器只按字符长度切，不认识表格结构。表格的语义靠表头说明，表头丢了，“423”到底是错误码还是 HTTP 状态码就无从判断，embedding 和大模型都会理解错。

**方案**：
- 表格逐行生成 chunk，每行写成“列名: 值”的形式，例如 `错误码: 20003；HTTP状态码: 423；……`，开头再加上表名或所在章节，作为上下文。
- 表格不设 overlap。行与行之间本来就互相独立，overlap 只会造成重复召回。
- 5 行以内的小表整表放进一个 chunk，保留行与行之间的对比关系，比如“一线城市 500、二线城市 300”。
- 大表按字数上限把相邻几行打包成一块，也支持按某一列分组打包。

**效果**：每块都能单独读懂。问“账号被锁了怎么办”能精确命中 20003 这一行。

**可以引出的话题**：表格数据量很大时，统计、筛选、排序类的问题（比如“400 类错误码有几个”）向量检索答不全，因为它只返回 top-k 条。这类数据应该存数据库，走 Text-to-SQL；向量库里只放表格的说明。

### 案例 2：PDF 两张表被解析成一张

**现象**：《数据库设计规范.pdf》切分后，出现“对象: 金额；规则: DECIMAL(12,2)”这样列名错位的块；“二、表设计”“三、字段类型”两个章节标题也找不到了。

**排查**：没有先改切分器，而是先打印解析器输出的 Markdown 看问题出在哪一步。结果发现 anydoc 把第一张表、中间的段落、“二、表设计”的 5 条列表和第二张表全部识别成了一张表，列表的 5 条还被拆到了两列里。

**根因**：PDF 本身不存储表格结构，解析器只能根据文字的位置去推测表格。这两张表列宽相同、间距又近，就被当成了同一张。

**方案**：
1. 换解析器对比。pymupdf4llm 和 pdfplumber 都能正确拆出两张表，最后选了 pymupdf4llm，因为它能直接输出带标题的完整 Markdown。
2. 在切分器里加一道兜底检查：单元格超过 200 字，或者单元格里出现“二、”“3. ”这类章节、列表编号时，判定这张表解析出错，降级成普通文本来切，避免生成列名错位的块。

**效果**：两张表各自独立，列名正确，章节标题也恢复了。

**注意**：PyMuPDF 是 AGPL 协议，闭源商用需要购买商业授权。如果有商用打算，可以换 MIT 协议的 pdfplumber，代价是要自己把表格和正文按位置拼回 Markdown。面试时提到这一点，说明你会考虑开源协议的合规风险。

### 案例 3：复杂 PDF 的 Markdown 噪声

自己生成了一份 11 页的复杂 PDF 做测试，里面有封面、页眉页脚、目录、多级标题、合并单元格、跨页表格、代码块、提示框和双栏排版。切分时暴露出几个问题：

| 问题 | 原因 | 修复 |
|---|---|---|
| 章节路径里带 `**`，比如 `**一、总则**` | 解析器把加粗的标题输出成 `## **一、总则**` | 标题和单元格先去掉 `**`，但不处理 `__`，否则会误删 `__init__` 这类标识符 |
| 目录页切出 8 个全是 `. . . .` 的块 | 目录被识别成了表格 | 跳过标题为“目录”的章节；超过一半的行都带引导点的表格，也判定为目录 |
| 路径变成“修订记录 > 目录” | 标题跳级（h1 后面直接出现 h3）时，原来按列表下标截断路径，算错了 | 改用标题栈：遇到新标题，先弹出同级和更低级的标题，再压入当前标题 |
| 路径重复，如“数据库设计规范 > 数据库设计规范” | 文件名和一级标题相同 | 去掉路径开头和文件名相同的那一级 |
| 页眉“内部公开 · 未经许可不得外传”混进正文 | 每页都有的页眉页脚被当成了正文 | 解析时设置 `header=False, footer=False` |

**可以讲的点**：先自己构造覆盖各种难点的测试文档，再逐个修。比等用户上传后才发现问题要高效。

### 案例 4：合并单元格与跨页表格

**现象 1**：“服务清单”表里，合并单元格下面那几行的列整体向左移了一位，变成“业务域: auth-service；服务名: Token 签发与校验”。

**根因**：解析表格行时用的是 `line.strip("|")`。`strip` 会把行首行尾连续的竖线全部去掉，`||auth-service|` 这一行开头那个空单元格就被一起删掉了，后面的列全部往前挪。

**修复**：行首、行尾各只去掉一个 `|`。

**现象 2**：合并单元格空出来的格子，我先试了用上一行的值向下补齐，结果把 order-service 补成了“用户域”，实际应该是“交易域”。

**根因**：PDF 里合并单元格的值不在合并区域的第一行，而是在垂直居中的那一行，所以没法判断该向上补还是向下补。

**决策**：放弃自动补齐，空单元格保持为空，生成 chunk 时跳过空字段。宁可少一个字段，也不能写错。

**现象 3**：一张 28 行的跨页表格被拆成两张，第二张的行号又从 1 开始。

**修复**：两张表紧挨着、在同一个章节下、表头也完全相同时，合并回一张。

### 案例 5：图片里的信息检索不到

**背景**：测试文档的图 5-3（柱状图）里有各级接口的响应时间上限（200 / 500 / 1000 / 3000 ms），这些数字只画在图里，正文没写。

**方案**：
1. pymupdf4llm 设置 `write_images=True`，把图片导出成文件，Markdown 里留下图片占位。
2. 用 Ollama 运行视觉模型 qwen3-vl:8b-instruct，逐张生成描述。提示词要求完整转录图中的文字和数字；如果是图表，要逐项列出每个类别对应的数值。识别时会把图片前后约 150 个字一起传给模型，帮它判断图片在讲什么。
3. 每张图生成一个 `type=image` 的 chunk，内容是“章节路径 + 图注 + 描述”，metadata 里存图片路径。
4. 宽或高小于 100 像素的图片当作装饰，直接跳过，例如解析时产生的一张 178×22 的碎图。

**踩过的坑**：图 5-2 的图注一直挂不上。排查后发现，pymupdf4llm 把它包在了 `<!-- Start of picture text -->` 这样的 HTML 注释里，切分前先去掉注释就好了。

**效果**：问“核心交易接口的响应时间上限是多少”，命中图 5-3，回答 200 ms。每张图识别约 2 秒，第一次调用要加载模型，大约 9 秒。

**取舍**：OCR 更快，也不需要 GPU，但看不懂图的结构：架构图只能得到一堆零散的方框名称，柱状图的数字和类别对不上。所以选了视觉大模型。

### 案例 6：txt 文档的问题都检索不到

**现象**：问“代码里能用 print 打日志吗”“常量怎么命名”，回答都没有来源，可答案明明就在《Python开发编码规范.txt》里。

**排查**（这是最能体现排查能力的一个案例）：
1. 检查入库结果：这份 txt 只切出了 3 个块，每块三四百字。
2. 计算问题和库里全部 82 个块的相似度：答案所在的块排第 39 名，相似度只有 0.276，没进入 rerank 的前 20 个候选，rerank 根本看不到它。
3. 对照实验：把答案那一句单独拿出来算相似度，是 0.737。说明内容本身是匹配的，问题出在切分粒度上。

**根因**：txt 没有 `#` 标题，切分器把整篇文档当成一个章节，只按长度切成几个大块。每块混了好几个章节的内容，向量被稀释了。

**方案**：加一个 `txt_to_markdown`，先把 txt 转成 Markdown 再切分：
- 下一行是 `===` 或 `---` 的，转成一级或二级标题。
- “一、xxx”“第二章 xxx”这类单独成行的短标题，转成二级标题。
- 连续几行列数相同、用 Tab 或多个空格对齐的内容，转成 Markdown 表格。

**效果**：从 3 块变成 9 块，8 个章节各一块，命名规范表单独一块。“print 打日志”的 rerank 分数到了 0.979，“常量命名”是 0.54，两题都带上了来源。另外两份 txt 测试文档也能正确识别出章节和表格。

**结论**：检索效果的上限，很大程度上在切分阶段就定了。chunk 太大会稀释向量，所以切分时一定要保留文档的结构。

### 案例 7：代码注释被识别成一级标题

**现象**：上传一本 313 页的技术书时，日志里的章节路径变成了 `AI-Agents-in-Depth > Agent 框架执行工具，添加结果到轨迹 {role: "tool", ...}`。

**根因**：PDF 里代码块的注释（比如 `# 第二次迭代`）被解析器原样输出成了 `#` 开头的行，切分器当成一级标题处理，后面的内容全挂到了这个假标题下面。我统计了一下，全书 510 个标题里有 118 个没有编号，大多是图注、表注、加粗的引导语和代码注释。

**方案**（迭代了两次）：
1. 第一版：含代码字符的“标题”不当成标题。但这一版误伤了真标题“1.1 现代 Agent = LLM + 上下文 + 工具”，`=` 被当成了代码特征。
2. 第二版：
   - 带编号的标题（1.2、第 3 章、实验 1-2），以及引言、后记、附录这类书籍固定结构标题，直接认定为真标题。
   - 代码特征只看花括号、引号和函数调用，不再单看 `=` 和 `[ ]`。
   - 如果文档是按编号组织的，那么没有编号、却会把编号标题从路径里挤掉的“标题”，按正文处理。级别更低的小标题（比如“深度思考”）照常保留。

**效果**：全书一级目录依次是引言、第 1 章到第 10 章、后记，顺序正确，章节路径里不再出现代码。之前那 16 份测试文档重新跑了一遍，切出的块数完全一样。

**可以讲的点**：改规则后不能只看问题有没有消失，还要检查有没有误伤。第一版规则的问题，是我把被过滤掉的标题逐条列出来检查时发现的。最后再把全部历史测试文档跑一遍，确认之前的效果没被改坏。

## 二、检索

### 案例 8：相似度阈值怎么定

**现象**：阈值一开始是 0.3。我用几个不相关的问题测了一下，“你好”得分 0.310，“Python 列表推导式怎么写”得分 0.375，都超过了阈值，会带出完全不相关的参考来源。

**方案**：写了一个评测脚本 `scripts/eval_threshold.py`，准备两组问题：一组知识库里有答案，一组没有。分别统计每个问题检索结果的最高分，阈值取在两组分数之间。最后定为 0.45：相关问题最低 0.463，无关问题最高 0.412。

**踩过的坑**：第一次跑出来两组分数是重叠的，相关问题最低只有 0.365。排查后发现，“相关问题”那组里有 5 个问题，答案所在的文档还没导入知识库，它们其实是无关问题，分数低是正常的。分好组之后，两组就不重叠了。由此学到：评测集必须和当前入库的数据对应，不然测出来的阈值是错的。

**可以讲的点**：阈值和 embedding 模型强相关，换模型或者文档变多之后要重新测，所以我把它做成了配置项加评测脚本，没有写死在代码里。

### 案例 9：引入 Rerank

**现象**：“单元测试覆盖率要求多少”这一题，向量检索排第一的块是“规范级别”那张表，里面没有答案；真正的答案在 CI/CD 流水线图的描述里，排在后面。

**方案**：
- 向量检索先召回 20 个候选，再用 Cross-Encoder 逐个给“问题 + 候选片段”打分，重新排序后取前 4 个。
- Ollama 不支持 rerank 接口（我测了 `/api/rerank`，返回 404），所以改用 fastembed 在进程内运行 `BAAI/bge-reranker-v2-m3-int8`。这个模型 0.57GB，Apache-2.0 协议，支持中文。同样支持中文的 jina-reranker-v2 是 CC-BY-NC 协议，不能商用，所以没选。
- 模型输出的分数没有上下限，用 sigmoid 换算到 0～1，方便设阈值。阈值也改用 rerank 的分数来定。

**效果**：

| | 只用向量检索 | 加 rerank 后 |
|---|---|---|
| 相关问题分数 | 0.46 ~ 0.75 | 大部分在 0.94 以上 |
| 无关问题分数 | 0.21 ~ 0.41 | 大部分低于 0.03 |
| 两组之间的间隔 | 0.05 | 0.24 |

**踩过的坑**：一开始候选只取 10 个，结果“单元测试覆盖率”又被过滤掉了。原因是答案块在向量检索里排第 13，根本没进候选。rerank 只能在候选里重新排序，召回阶段漏掉的它找不回来。改成 20 个就好了。

**代价**：CPU 上给 20 个候选打分平均 1.9 秒，10 个是 0.74 秒；第一次运行要下载模型，大约 2 分钟。

### 案例 10：rerank 读不懂“禁止新增”，补关键词检索

**现象**：问“jQuery 还能用吗”。向量检索已经把 jQuery 那一行排在第一，答案就在里面（状态是“禁止新增”），但 rerank 只打了 0.037 分，被阈值过滤掉了。

**排查**：把这一行单独拿出来让 rerank 打分，也只有 0.053，说明不是候选太少或者块太大，而是 rerank 模型对不上“还能用吗”和“禁止新增”这两种说法。

**为什么不靠调阈值解决**：无关问题“前端用什么 CSS 框架”的 rerank 分数是 0.372，比相关问题“周五下午能发布上线吗”的 0.336 还高。调低阈值会放进无关来源，调高又会误伤正常问题。

**方案**：加关键词检索。
- 从问题里提取专有名词，比如 jQuery、10005、inventory-service，用 Chroma 的 `where_document={"$regex": ...}` 直接匹配原文，没有加新依赖。
- 只用“专一”的词：命中超过 3 个块的词（Python 命中 12 块，Kafka 7 块，main 7 块）太常见，不当关键词用。这个数做成了配置项 `KEYWORD_MAX_HITS`。
- 命中关键词的块加入 rerank 的候选，即使分数低于阈值也保留。

**效果**：jQuery 这题现在能答对：“状态为禁止新增，仅用于老旧系统”。42 道题的完整问答测试里，41 道一次就过了，没过的一道（CSS 框架）见案例 13。

**可以讲的点**：这就是常说的混合检索。向量检索擅长理解意思，关键词检索擅长找专有名词和编号，两者互补。

## 三、回答的可信度

### 案例 11：模型不调用检索工具，回答没有来源

**现象**：“熔断阈值推荐设置多少”这一题没有来源。回答是“通常建议 50% 错误率或连续 5 次失败”，其中“连续 5 次失败”文档里根本没有，是模型编的。

**排查**：
1. 查数据库里的对话记录，这条回答的来源数是 0；同一会话前面三个问题都有来源。
2. 单独测检索：答案块的相似度是 0.58，远高于阈值。所以只要调用了工具，就一定能查到。
3. 复现：不带历史单独问 3 次，每次都调用了工具；带上那个会话的 6 条历史再问 4 次，有 1 次没调用工具。

**根因**：要不要检索是模型自己决定的。前几轮聊的都是同一份文档，模型觉得自己已经知道了，就跳过了检索。8B 模型不会每次都照提示词做。我还看了 `langchain_ollama` 的源码，`bind_tools` 里的 `tool_choice` 参数被标成了未使用，没法强制它调用工具。

**方案**：每轮先由代码用原问题检索一次，把结果作为参考资料和问题一起交给模型。检索工具还保留着，参考资料不够时模型可以换关键词再查。存进数据库的是用户的原问题，历史记录也从数据库读，所以参考资料不会带进后面的对话。

**效果**：同样的场景测了 3 次，每次都有来源。

### 案例 12：模型编造答案和引用来源

**现象 1**：回答写着“根据《Python开发编码规范.txt》”，实际来源数是 0。“常量怎么命名”这题还说依据的是《微服务开发规范.pdf》，并且编了一套命名规则。

**修复 1**：提示词里加了一条规则：文件名只能取自参考资料，没有参考资料时不写任何文件名。

**现象 2**：后来测“年假有几天”，没检索到任何资料，模型却编出“满 1 年未满 10 年享 10 天”，还引用了一份不存在的《员工手册2023版》。同一题之前跑是正常的，说明编造是随机出现的。

**根因**：没检索到资料时，原来只把问题本身交给模型，模型不知道知识库里其实没有答案，就会用自己的知识补上。

**修复 2**：没检索到资料时，明确告诉模型“知识库中没有检索到相关内容，请换关键词再查一次，还找不到就回答未找到，不要凭自身知识作答”。

**效果**：6 个容易引发编造的问题各跑 3 次，共 18 次，都没有编造。

**可以讲的点**：
- 编造的出处比没有出处更危险，因为用户会相信它。
- 提示词的约束是概率性的，所以要多跑几次验证，不能测一次就算过。

### 案例 13：回答“未找到”却挂着来源

**现象**：问“前端用什么 CSS 框架”，回答说“知识库中暂未找到”，下面却显示了一条来源（技术栈清单，0.372 分）。

**方案**：没有去调阈值（原因见案例 10）。改成：只要回答里出现兜底话术“知识库中暂未找到相关内容”，就清空来源，前端显示和数据库保存的都是空的。

**顺带**：同时收紧了助手的回答范围：写诗、讲笑话、通用编程教学这类请求，礼貌说明自己只回答公司相关的问题；打招呼、道谢照常回复。

## 四、工程

### 案例 14：上传大文档时弹窗一直 loading

**现象**：上传接口是同步的：保存文件、解析、识别图片、切分、写入向量库，全部做完才返回。大文档要处理几十秒，这段时间弹窗一直显示 loading。

**方案**：把上传和处理拆开。
- 上传接口只保存文件，写一条“排队中”的记录，然后立即返回。解析和入库放到后台线程池里执行。
- 线程池只开 1 个线程，同一时间只处理一个文档。识图和 rerank 都要用 GPU 上的大模型，几个文档同时跑会抢显存，整体反而更慢。
- 数据库加了一个 `progress` 字段，状态从三种扩展成四种：排队中、处理中、已向量化、失败。每进入一个阶段就更新一次，比如“识别图片 3/5”“写入向量库 128/1412”。
- 后台线程拿不到 Flask 的请求上下文，所以把 app 对象传进去，在线程里自己创建应用上下文，再按 ID 重新查询文档。
- 前端在当前页还有未完成的文档时，每 3 秒刷新一次列表，刷新时表格不显示 loading，避免闪烁；全部完成后停止刷新，离开页面时也会停止。
- 处理中的文档不允许删除或重建索引，否则后台任务可能在删除之后又把向量写回去。
- 服务重启后，进程内的任务队列就没了，处理中的文档会一直卡在“处理中”。所以启动时会把这类文档改成“失败”，提示用户重建索引。

**效果**：上传接口 0.07 秒返回，整篇文档 17 秒处理完，进度能一路显示到完成。我还测了后台任务会不会拖慢接口：在 PDF 处理期间，每 20 毫秒检测一次主线程的延迟，最大 76 毫秒。

**为什么不用 Celery**：Celery + Redis 是生产环境的标准做法：任务持久化，重启不会丢；还能单独扩容 worker。但这个项目用单进程部署就够了，引入 Redis 和单独的 worker 进程成本太高。线程池方案唯一的问题是重启会丢任务，启动时的处理已经兜住了。以后要换 Celery，只需要改提交任务那一行。

**局限**：这个方案只适合单进程部署。改用 gunicorn 多进程时，每个进程各有一个队列，而且一个进程重启时，会把其他进程正在处理的文档误标成失败，到时候必须换成 Celery。

### 案例 15：313 页 PDF 上传失败

**现象**：上传一本 313 页的技术书，状态变成“失败”。界面上看到的是一条“表格疑似解析错误”的警告，但这条只是降级提示，并不是失败原因。

**排查**：
1. 查数据库里的 `error_msg`：`Post "http://127.0.0.1:51257/tokenize": ... actively refused it. (status code: 400)`。
2. 查 Ollama 的日志，按时间线还原：115 张图片都识别完了；最后一个 `/api/embed` 请求处理了 46 秒，返回 400。
3. 原因是一次把 1000 多个片段交给 embedding 模型，单个请求太大，处理过程中连接断开了。之前的测试文档最多只有几十个片段，所以一直没暴露这个问题。

**方案**：每批 64 个片段分批写入。单批失败自动重试，最多 3 次，每次重试前等待的时间逐次加长。进度显示到批次，比如“写入向量库 128/1412”。

**效果**：用一个临时集合测试，200 个片段分 4 批写完，用时 9.6 秒，测试数据没有写进正式的向量库。按这个速度，全书 1412 个片段大约 70 秒写完。

**可以讲的点**：
- 小数据上没问题，不代表大数据上也没问题。批量操作要分批，还要考虑失败重试。
- 表面上的报错不一定是真正的原因，要去查数据库记录和下游服务的日志。

### 案例 16：MCP stdio 服务的 stdout 污染

**背景**：把开源项目 prompt-optimizer 的 MCP 服务接入 Claude Code，用来优化各个 Agent 的提示词。

**问题和处理**：
- stdio 模式下，stdout 是专门用来传 JSON-RPC 消息的，但它的代码会用 `console.log` 往 stdout 打日志，可能导致客户端解析失败。我没有改它的源码，而是加了一个启动脚本，先把 `console.log` 转到 stderr，再加载服务。这样以后 `git pull` 更新也不会冲突。
- 它的 HTTP 模式会监听所有网卡，而且没有鉴权，同一局域网里的人能用我的 API Key 调用，所以选了 stdio 模式。
- 项目要求 Node 24，我本机是 Node 25。用 nvm 额外装了 Node 24，在 MCP 配置里写它的绝对路径，没有切换全局版本。
- API Key 只放在被 gitignore 忽略的 `.env.local` 里，不写进 Claude Code 的配置。

**验证**：手动发送 `initialize` 和 `tools/list` 请求，stdout 里没有混进非 JSON 的内容，3 个工具都能正常列出来。

## 五、代码细节小问题

这些不适合单独作为案例讲，但面试官追问细节时可以拿来说明你对代码足够熟悉：

- 打包函数 `_pack` 的条件写反了（`size < max_chars`），结果每加一行就输出一批，大表永远是一行一块。表现出来就是 `row_start` 和 `row_end` 总是相等。
- 小表的多个 chunk 共用了同一个 metadata 字典，修改其中一个会影响其他几个。改成每个 chunk 复制一份。
- 调用 `split_markdown(text, doc)` 时，把数据库对象传到了 title 参数的位置，少传了 `base_metadata`。而外层的 `except` 吞掉了异常，所以没看到报错。教训：调试期间不要静默吞异常。
- 前端分页组件写的是 `@current-change="loadList"`，页码会被当成 `loadList` 的第一个参数 `silent` 传进去，导致翻页时不显示 loading。改成 `loadList()`。
- 修改 `.env` 时，换行符被改成了 LF，事后才发现，又改回了 CRLF。修改配置文件前要先备份，改完对比一下除了新增项之外是否完全一致。

## 六、高频追问

**为什么所有格式都先转成 Markdown？**
这样切分逻辑只用写一套。各格式的解析器只负责把内容转成 Markdown，切分器只认 Markdown 里的标题、表格和图片。新增一种格式时，只需要写它的转换函数。

**chunk_size 怎么定的？**
正文用 500 字、overlap 50 字，中文按段落、句号等依次回退切分；表格按行或按字数上限打包。这两个值没有严格调过参，是按经验设的。真要优化，应该和阈值一样用评测集来测。如实回答这一点比编一个理由更好。

**怎么评估检索效果？**
目前有两种：阈值评测脚本，看相关和无关两组问题的分数分布；42 道题的端到端测试，检查每题的来源里是否包含答案所在的块，以及没有来源时回答里有没有编造出处。还没做的是系统化的指标，比如 Recall@k、MRR，以及用 LLM 给回答质量打分。

**为什么用本地模型，而不是调云端 API？**
企业内部文档不能发到外部服务。本地模型的代价是能力弱，会出现不调用工具、编造内容等问题，所以要在工程上补：每轮先由代码检索、回答“未找到”时清空来源、给模型明确的兜底提示。

**向量检索和关键词检索怎么合并？**
关键词检索命中的块加入 rerank 的候选，即使分数低于阈值也保留。我没有用 RRF（倒数排名融合），因为后面还有 rerank 统一排序，而且关键词检索只用来补充专有名词这一类场景。

**数据量变大以后，哪些地方会先撑不住？**
1. 关键词检索：Chroma 的正则匹配是全量扫描，文档多了会变慢，到时候要换成 BM25 倒排索引或 Elasticsearch。
2. 进程内任务队列：多进程部署时必须换 Celery。
3. rerank：在 CPU 上跑，候选数和延迟成正比，要么改用 GPU，要么减少候选数。
4. 阈值：文档领域变杂以后，分数分布会变化，需要重新测。

## 七、已知局限

面试时主动说出局限，比被面试官问出来要好：

- “日志里哪些信息要脱敏”只答出了一部分：Python 规范里“密码、token”那一句 rerank 只打了 0.081 分，没被选上。这是 rerank 模型判断上的局限，靠调参数解决不了。
- 关键词检索：只要原文里出现问题中的专有名词，这个块就一定会被保留。如果问的是同名但不相关的东西，可能带出一条无关来源。
- 代码块被解析器压成了一行，字段名和注释都在，按关键词还能搜到，但格式丢了。
- 前端还不能显示原图。chunk 里已经存了图片路径，要展示原图，还需要后端提供一个带权限校验的图片访问接口。
- 评测集只有几十个问题，结论的统计意义有限。
- 视觉模型识别速度大约每张 2 秒，图片多的文档处理时间会比较长。
